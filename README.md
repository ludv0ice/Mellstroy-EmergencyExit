# Этап 1. ORM-модели и миграция базы данных

Тема: «Создание и тестирование АРМ марафона по бегу».
Студент: Ченцов Руслан Игоревич. Группа в задании указана как ИП-41/ИП-41к; конкретную группу следует уточнить при оформлении итоговой записки.

## Границы этапа
Реализованы структура PostgreSQL, 16 ORM-моделей SQLAlchemy (каждая в отдельном файле), начальная обратимая миграция Alembic, тестовые данные, интеграционные тесты и основа FastAPI. Создание предметных маршрутов, Pydantic-схем, авторизация, отчеты Word/Excel и Django относятся к следующим этапам по фотографии. В /docs пока нет предметных операций.

## Развертывание
Нужны Python 3.10+ (проверено на 3.12) и Docker Compose либо установленная PostgreSQL 16.
Из корня распакованного проекта:

```bash
python -m venv .venv
# Linux/macOS:
source .venv/bin/activate
# Windows PowerShell вместо предыдущей команды:
# .venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
docker compose up -d --wait db
alembic upgrade head
alembic current
alembic check
python -m scripts.seed
uvicorn app.main:app --reload
```
Документация FastAPI: http://127.0.0.1:8000/docs. Секретов для запуска нет. Пароль marathon_local предназначен только для локальной учебной БД. При изменении POSTGRES_PASSWORD укажите соответствующий DATABASE_URL. Файл .env.example — пример; приложение автоматически .env НЕ читает. Без DATABASE_URL используется локальное подключение из app/database.py.

Linux/macOS: `export DATABASE_URL='postgresql+psycopg://marathon:marathon_local@localhost:5432/marathon'`.
PowerShell: `$env:DATABASE_URL='postgresql+psycopg://marathon:marathon_local@localhost:5432/marathon'`.
Существующая установка PostgreSQL: создайте пользователя и пустую БД, затем задайте URL. Не вызывайте Base.metadata.create_all(): структура создается миграциями.

## Проверка и откат
Создайте отдельную пустую тестовую БД:

```bash
docker compose exec db createdb -U marathon marathon_test
# Linux/macOS:
export TEST_DATABASE_URL='postgresql+psycopg://marathon:marathon_local@localhost:5432/marathon_test'
# PowerShell: $env:TEST_DATABASE_URL='postgresql+psycopg://marathon:marathon_local@localhost:5432/marathon_test'
python -m pytest -q
```
Тесты отказываются работать с непустой БД; создают таблицы миграцией, заполняют их, проверяют ограничения и откатывают схему. Используйте только отдельную тестовую БД. Проверка `alembic check` входит в тестовый цикл. Для рабочей учебной БД `alembic downgrade base` удаляет ВСЕ таблицы и данные проекта; предварительно сохраните нужные данные. Повторное заполнение непустой БД намеренно запрещено. `docker compose down` сохраняет том с данными.

## Демонстрационные данные
Все данные синтетические, не являются сведениями о реальных людях или мероприятиях. Создаются 50 исторических выпусков учебного ежегодного марафона (1976–2025), по три забега на выпуск, 50 бегунов, 50 спонсоров, 50 соглашений, 50 результатов, 50 сертификатов, 50 волонтеров, 50 назначений, 50 новостей и 50 достижений. Пользователей 100, назначений ролей 101. Справочники содержат по 3 записи: дистанции 5/21/42 км согласно ТЗ и роли runner/coordinator/admin. Анонимный посетитель не хранится в БД как учетная запись. Учетные записи отключены, поле password_hash содержит маркер запрета входа; рабочих паролей нет.

## Структура
- app/models/ — отдельный файл для каждой сущности, связи relationship и ограничения.
- app/database.py — базовый класс, фабрики engine и session; секреты читаются из окружения.
- app/main.py — объект FastAPI для продолжения работы на следующем этапе.
- migrations/ — конфигурация и явные upgrade/downgrade; миграция не зависит от актуальных моделей.
- scripts/seed.py — атомарное заполнение демонстрационными данными.
- tests/ — проверки миграции, наполнения, связей и ограничений на PostgreSQL.
- docs/ — пояснение проектных решений, ERD, словарь каждого поля, SQL и результаты проверки.

## Принятые решения
Регистрация связывает бегуна с конкретным забегом, забег — дистанцию с ежегодным мероприятием. Бегун может участвовать в нескольких забегах; повторная регистрация на тот же забег запрещена. Спонсорство относится к регистрации, поэтому условия и сумма сохраняются отдельно для каждого участия. Номер участника уникален в пределах забега. Результат и сертификат имеют связь один-к-одному с регистрацией. Числовое время хранится в секундах; место в рейтинге вычисляется сортировкой результатов finished внутри забега по времени, при равном времени участники делят место (SQL RANK), dns/dnf/dsq исключаются. Сам рейтинг не дублируется в профиле бегуна.

Связь пользователей и ролей многие-ко-многим реализована через user_roles. Роль coordinator предусмотрена для подтверждения соглашений, но проверка прав будет добавлена на этапе авторизации. Суммы хранятся как NUMERIC(12,2), не float. Даты стартов и действий имеют часовой пояс; тексты поддерживают Unicode. Язык новостей хранится явно; локализация интерфейса — следующий этап.

В БД обеспечены PK/FK/UNIQUE/NOT NULL/CHECK, запрет отрицательных сумм, недопустимых дистанций, времени и смен, согласованность полей подтверждения спонсорства. Удаление предметных данных по FK запрещено RESTRICT для сохранения истории; удаление пользователя каскадно удаляет только назначения ролей. Основные бизнес-сущности удаляются явно с учетом зависимостей.

Межтабличные правила (лимит мест, дата рождения до забега, роль подтверждающего координатора, выдача finish-сертификата только после результата finished, допустимые переходы статусов и пересечение смен волонтеров) требуют транзакционного сервисного слоя последующих этапов. На этом этапе они не объявляются реализованными. Документы представлены ссылками, загрузка файлов пока не реализована. Схема приведена к 3НФ: справочники отделены, связи многие-ко-многим раскрыты, вычисляемые рейтинги не хранятся.
